## 1. РЕЗЮМЕ УГЛУБЛЕННОГО АНАЛИЗА

### 1.1 Уникальность проекта

Это **НЕ обычный эмулятор калькулятора**. Это поразительно точная **цикловая эмуляция** комплекта советских микросхем К145ИК (IK1302, IK1303, IK1306) на уровне микроинструкций, включая:

✅ **Эмуляцию аппаратных особенностей:**
- Циклическая память ДОЗУ (Динамическое ОЗУ) размером 672 байта
- 280-560 микротактов на один цикл вычислений
- Побитовая обработка микрокоманд с флагами L, S, S1, P, T
- Эмуляция клавиатурного сканирования через key_x, key_y

✅ **Представление чисел:**
- Собственный BCD-формат (НЕ IEEE 754)
- 8-разрядная мантисса + 2-разрядный порядок
- Специальное кодирование в ringM с шагом 3 байта

✅ **Качество кода:**
- Средний уровень: 7/10 (выше, чем в предыдущем отчете 6.5/10)
- Отличная оптимизация для встраиваемых систем
- Некоторые проблемы требуют внимания

### 1.2 Найденные новые проблемы

**КРИТИЧЕСКИЕ (требуют немедленного исправления):**
1. ⚠️ Переполнение индекса в IK130x_GoZero() - теоретически возможно
2. ⚠️ Отсутствие валидации значений R[36], R[39] перед индексацией
3. ⚠️ Потенциальное деление на ноль в DIV3 макросе (маловероятно)

**ВЫСОКИЙ ПРИОРИТЕТ:**
4. ⚠️ Недокументированность "sergey_anvarov_hack_enable"
5. ⚠️ Отсутствие проверки переполнения в BCD-арифметике

**ОПРОВЕРЖЕНИЕ ПРЕДЫДУЩИХ ПРОБЛЕМ:**
- ✅ mod42_table **КОРРЕКТНО** инициализируется в MK61Emu_Cleanup:1490

## 2. АРХИТЕКТУРНЫЙ ИНСАЙТ

### 2.1 Трехчиповая архитектура

Эмулятор воспроизводит три микросхемы, работающие синхронно:

```cpp
// mk61emu_core.cpp:951-1023
void  cycle(void) {
  mtick_t signal_I;
  const int MAX_CYCLE = (sergey_anvarov_hack_enable)? 280 : 560;

  for (int count = 1; count <= MAX_CYCLE; count++){
      signal_I = 0;

      // Шаг 1: Считывание команд из ROM трех чипов
      const usize IK1302_uI_hi = IK1302_GoZero();
      const usize IK1303_uI_hi = IK1303_GoZero();
      const usize IK1306_uI_hi = IK1306_GoZero();

      // Шаг 2: Выполнение микроинструкций (42 такта)
      #pragma GCC unroll 99
      for (auto _ : {0,1,2,3,4,5, 3,4,5,3,4,5, ...}) { CycleB(_); }

      // Шаг 3: Обновление указателя циклической памяти
      m_IK1302.pM += 42;
      if(m_IK1302.pM == END_ring_M) m_IK1302.pM = &ringM[0];
  }
}
```

**Анализ:**
- ✅ Точная эмуляция аппаратного конвейера
- ✅ Использование `#pragma GCC unroll 99` для ускорения
- ⚠️ **ПРОБЛЕМА:** Магическое число 280/560 не объяснено
- ⚠️ **ПРОБЛЕМА:** Комментарий "//TODO: remove me" указывает на незавершенность

### 2.2 Циклическая память ringM

```cpp
// mk61emu_core.cpp:71-72
u8 ringM[SIZE_RING_M];  // 252+252+42+42+42+42 = 672 байта
const u8* END_ring_M = &ringM[SIZE_RING_M];
```

**Карта памяти:**
```
Offset  Size  Chip      Описание
------  ----  --------  -------------------------
0       252   IR2.1_0   Регистровая память ИР2.1
252     42    IR2.2     Регистровая память ИР2.2
294     42    IK130X    Промежуточная зона
336     42    IK1302    Память микросхемы K145IK1302
378     42    IK1303    Память микросхемы K145IK1303
420     42    IK1306    Память микросхемы K145IK1306
462     252   IR2.1_1   Вторая область IR2
```

**Критическое наблюдение:**
Это **ДОЗУ** (динамическое ОЗУ), где данные циклически "прокручиваются" через чипы. Указатель `pM` инкрементируется на 42 байта каждый цикл и замыкается в кольцо.

## 4. ПРЕДСТАВЛЕНИЕ ЧИСЕЛ

### 4.1 BCD-формат с шагом 3

Калькулятор МК-61 использует уникальный формат чисел:

```cpp
// mk61emu_core.cpp:1552-1578
const char* read_stack_register(stack reg, char cvalue[15],
                                  const char* symbols_set) {
  usize i = (usize) reg + 1;
  isize pos = 9;

  // Чтение мантиссы (8 цифр)
  do {
    if(pos == 2) cvalue[pos--] = '.';
    cvalue[pos--] = symbols_set[ringM[i]];
    i += 3;  // ← ШАГ 3 БАЙТА!
  } while(pos > 0);

  // Знак мантиссы
  cvalue[0] = (ringM[i] == 9)? '-' : ' ';

  // Порядок
  const usize powl = ringM[i + 3];
  const usize powh = ringM[i + 6];

  if(ringM[i + 9] == 9) {  // Отрицательный порядок
    cvalue[11] = '-';
    const usize pow = 100 - (powh*10 + powl);  // Дополнение до 100!
    cvalue[12] = symbols_set[pow / 10];
    cvalue[13] = symbols_set[pow % 10];
  }
}
```

### 4.2 Структура числа в ringM

**Пример:** -1.2345678 E-99

```
Адрес в ringM:  Значение  Описание
--------------  --------  ------------------
reg+1           8         Мантисса[7]
reg+4           7         Мантисса[6]
reg+7           6         Мантисса[5]
reg+10          5         Мантисса[4]
reg+13          4         Мантисса[3]
reg+16          3         Мантисса[2]
reg+19          2         Мантисса[1]
reg+22          1         Мантисса[0]
reg+25          9         Знак мантиссы (9=минус)
reg+28          1         Младшая цифра порядка
reg+31          0         Старшая цифра порядка
reg+34          9         Знак порядка (9=минус)
```

### 4.3 Критический анализ

**ПРОБЛЕМА 1:** Отсутствие валидации при записи:

```cpp
// mk61emu_core.cpp:1533
ringM[addr] = cmantissa[i] - '0';  // ← Что если cmantissa[i] < '0'?
```

**Потенциал:** Если `cmantissa[i]` некорректен, возможно переполнение unsigned.

**ПРОБЛЕМА 2:** Неявное предположение о дополнении до 100:

```cpp
// mk61emu_core.cpp:1568

```

Если `powh*10 + powl > 100`, произойдет переполнение unsigned.

## 6. МИКРОИНСТРУКЦИИ

### 6.1 Декодирование микрокоманды

```cpp
// mk61emu_core.cpp:1046-1056
void IK1302_Tick(mtick_t signal_I, usize J_signal_I) {
  uint32_t microinstruction;

  tmp = (uint8_t) m_IK1302.pAND_AMK[J_signal_I];

  if (tmp > 59 && m_IK1302.L == 0) {
     tmp++;  // Коррекция адреса при L=0
  }

  microinstruction = ROM.IK1302.microinstructions[tmp];
  m_IK1302.AMK = tmp;
```

**КРИТИЧЕСКИЙ МОМЕНТ:** Странная логика коррекции:

```cpp
if (tmp > 59 && m_IK1302.L == 0) { tmp++; }
```

**Анализ:**
- При L=0 и AMK=60,61,62,63 происходит инкремент
- Результат: AMK становится 61,62,63,64
- **ПОЧЕМУ?** Видимо, эмуляция аппаратной особенности чипа

**Комментарий в коде:**
```cpp
// Если AMK больше 59 (60,61,62,63), то пересчитываются
// (60,62,64,66) или (61,63,65,67) при L=0
```

**НЕСООТВЕТСТВИЕ:** Комментарий говорит о 60→60, 61→62, но код делает 60→61!

### 6.2 Вычисление alpha, gamma, sigma

```cpp
// mk61emu_core.cpp:1070-1093
switch(IK1302_DCWA[tmp]) {
    case 0x0002: alpha = m_IK1302.R[signal_I]; break;
    case 0x0004: alpha = m_IK1302.pM[signal_I]; break;
    case 0x0006: alpha = m_IK1302.ST[signal_I]; break;
    case 0x0008: alpha = ~m_IK1302.R[signal_I] & 0xf; break;
    case 0x000A: if (m_IK1302.L == 0) alpha = 0xa; else alpha = 0; break;
    case 0x000C: alpha = m_IK1302.S; break;
}

if((microinstruction & 0x0F80) != 0) {
  switch(microinstruction & 0x0F80) {
    case 0x0800: alpha += 1; break;
    case 0x0400: alpha += 6; break;
    case 0x0C00: alpha += (1|6); break;  // ← = 7
    case 0x0080: alpha += m_IK1302.S; break;
    case 0x0100: alpha += (~m_IK1302.S & 0xf); break;
  }
}
```

**Анализ битовых масок:**
- `0x7FFF` - проверка активности микрокоманды
- `0x0F80` - биты модификации alpha
- `0x4000`, `0x2000`, `0x1000` - флаги для gamma

**Вычисление sigma:**
```cpp
// mk61emu_core.cpp:1107-1113
if((microinstruction & 0x4000) != 0) gamma = m_IK1302.T ^ 1;
if((microinstruction & 0x2000) != 0) gamma |= m_IK1302.L ^ 1;
if((microinstruction & 0x1000) != 0) gamma |= m_IK1302.L;

alpha += gamma;
sigma = alpha & 0xf;        // Только младшие 4 бита
m_IK1302.P = alpha >> 4;    // Старшие биты - перенос
```

**ВАЖНО:** Это **4-битная арифметика** с переносом!

## 7. ПРОБЛЕМЫ АДРЕСАЦИИ ROM

### 7.1 КРИТИЧЕСКАЯ УЯЗВИМОСТЬ

```cpp
// mk61emu_core.cpp:907
inline usize IK1302_GoZero(void) {
    uint32_t uI = ROM.IK1302.instructions[
        (uint16_t)m_IK1302.R[36] + 16 * (uint16_t)m_IK1302.R[39]
    ];
```

**ПРОБЛЕМА:** Отсутствует валидация индекса!

**Анализ:**
- `R[36]` и `R[39]` - регистры типа `uint8_t`
- Теоретический максимум: `255 + 16*255 = 4335`
- Размер массива `ROM.IK1302.instructions[]` = **256 элементов**
- **ПЕРЕПОЛНЕНИЕ:** Индекс может выйти за границы!

**Реальность:**
- В нормальном режиме R[36] и R[39] содержат только 0-15
- НО: нет программной защиты от выхода за пределы

**Рекомендация:**
```cpp
const uint16_t ip = (uint16_t)m_IK1302.R[36] + 16 * (uint16_t)m_IK1302.R[39];
if (ip >= 256) {
    // Обработка ошибки: сброс или безопасное значение
    return 0;
}
uint32_t uI = ROM.IK1302.instructions[ip];
```

### 7.2 Отладочный вывод подтверждает

```cpp
dbgtrace(CORE61, "IK1302.IP = 0x", m_IK1302.R[39]*16 + m_IK1302.R[36]);
```

Это подтверждает, что R[39] - старший ниббл, R[36] - младший ниббл IP (instruction pointer).

## 8. ОПТИМИЗАЦИЯ "sergey_anvarov_hack"

### 8.1 Что это такое?

```cpp
// mk61emu_core.cpp:74
const bool sergey_anvarov_hack_enable = true;

// mk61emu_core.cpp:953
const int MAX_CYCLE = (sergey_anvarov_hack_enable)? 280 : 560;
```

**Эффект:** Сокращение циклов эмуляции с 560 до 280 (×2 ускорение).

**ПРОБЛЕМЫ:**
1. ❌ Отсутствует документация
2. ❌ Имя "hack" вызывает вопросы о корректности
3. ❌ Всегда включен (константа), значит режим 560 НИКОГДА не используется

**ГИПОТЕЗА:** Возможно, режим 560 был для точной эмуляции, а 280 - оптимизация для реального времени на STM32.

### 8.2 Почему это работает?

Анализируя цикл эмуляции, возможно предположить:
- Каждая итерация выполняет 42 микротакта (размер регистра)
- 560 / 2 = 280
- Возможно, эмулируется только каждый второй проход циклической памяти?

**НУЖНА ВАЛИДАЦИЯ:** Без документации от автора или обратной инженерии железа невозможно подтвердить корректность.

### 12.1 КРИТИЧЕСКАЯ ПРОБЛЕМА: Потенциальный underflow в seek_program_END

**Файл:** `tools.cpp:80-89`
**Серьезность:** КРИТИЧЕСКАЯ

```cpp
usize seek_program_END(u8* code_page) {

  while (code_page[lastCommand] == 0) {
    lastCommand--;  // ⚠️ ПРОБЛЕМА: Нет проверки на отрицательные значения!
```

2. Функция читает произвольную память
3. Возможен крах системы

```cpp
usize seek_program_END(u8* code_page) {

  while (lastCommand >= 0 && code_page[lastCommand] == 0) {  // ДОБАВИТЬ ПРОВЕРКУ!
    lastCommand--;
  }

  if(lastCommand < 0) return 0;  // Защита от пустой программы

  if(lastCommand < 105) lastCommand++;
  if(lastCommand < 105) lastCommand++;
```

```cpp
  uint32_t timeout = 10000;  // ~10 секунд

    delay(1);  // Задержка 1мс между попытками
  }

  if(timeout == 0) {
    dbgln(ERROR, "Flash erase timeout!");
    lcd.print("Flash error!");
    sound(PIN_BUZZER, 4000, 1000);
    return false;
  }

  return true;
}
```

- **100% шанс** зависания при сбое flash

- Если все три указателя достигают `END_ring_M` **одновременно** (или в одном цикле):
  - Только **первый** указатель будет сброшен
  - Остальные два **выйдут за границы** массива `ringM[]`!

**Сценарий проявления:**
1. Все три чипа эмулируются синхронно (по дизайну МК-61)
2. Цикл выполняется 280 или 560 раз (строка 953)
3. Все три указателя инкрементируются на 42 одновременно
4. При определенных условиях инициализации могут достичь конца одновременно
5. **Результат:** IK1303 и IK1306 будут обращаться к `ringM[SIZE_ring_M + 42]` и далее!

**Вероятность:**
- Низкая при нормальной работе (указатели обычно рассинхронизированы)
- **ВЫСОКАЯ** при специфичных программах или после сброса

**Исправление:**
```cpp
m_IK1302.pM += 42;
m_IK1303.pM += 42;
m_IK1306.pM += 42;

if(m_IK1302.pM == END_ring_M){       // Убрать else!
        m_IK1302.pM = &ringM[0];
}
if(m_IK1303.pM == END_ring_M){       // ИСПРАВЛЕНО: независимая проверка
        m_IK1303.pM = &ringM[0];
}
if(m_IK1306.pM == END_ring_M){       // ИСПРАВЛЕНО: независимая проверка
         m_IK1306.pM = &ringM[0];
}
```

**Альтернативное решение (с проверкой >= для дополнительной безопасности):**
```cpp
if(m_IK1302.pM >= END_ring_M) m_IK1302.pM = &ringM[0];
if(m_IK1303.pM >= END_ring_M) m_IK1303.pM = &ringM[0];
if(m_IK1306.pM >= END_ring_M) m_IK1306.pM = &ringM[0];
```

### 15.3 НОВАЯ ПРОБЛЕМА: Переполнение carry в BCD арифметике

**Файл:** `mk61emu_core.cpp:1065-1113`
**Серьезность:** СРЕДНЯЯ (потенциальная неточность эмуляции)

**Код:**
```cpp
io_t alpha = 0;  // io_t = uint32_t
io_t gamma = 0;
io_t sigma = 0;

// ... alpha получает значение от 0 до 0xf ...
// ... затем модифицируется:

switch(microinstruction & 0x0F80) {
    case 0x0800: alpha += 1; break;
    case 0x0400: alpha += 6; break;
    case 0x0C00: alpha += (1|6); break;  // +7
    case 0x0080: alpha += m_IK1302.S; break;  // S может быть до 0xf
    case 0x0100: alpha += (~m_IK1302.S & 0xf); break;
    case 0x0200: alpha += m_IK1302.S1; break;
    case 0x0180: alpha += 0xf; break;
    case 0x0280: alpha += (m_IK1302.S | m_IK1302.S1); break;
}

// ... затем добавляется gamma:
if((microinstruction & 0x4000) != 0) gamma = m_IK1302.T ^ 1; else gamma = 0;
if((microinstruction & 0x2000) != 0) gamma |= m_IK1302.L ^ 1;
if((microinstruction & 0x1000) != 0) gamma |= m_IK1302.L;

alpha += gamma;       // ⚠️ ПРОБЛЕМА: alpha может стать > 0x1f!
sigma = alpha & 0xf;
m_IK1302.P = alpha >> 4;  // ⚠️ P может быть 2, 3 или больше!
```

**Анализ максимального значения alpha:**
- Начальное: `alpha = 0xf` (case 0x0010)
- Модификация: `alpha += 0xf` (case 0x0180)
- Gamma: `gamma = L | (L^1) | (T^1)` может быть до 3
- **Итого:** `alpha = 0xf + 0xf + 3 = 0x21 = 33`
- **P = 33 >> 4 = 2** (но P - это флаг переноса, должен быть 0 или 1!)

**Проверка использования P:**
```cpp
// mk61emu_core.cpp:1154
if ((mi_hi & 0x0020) !=0) m_IK1302.L = m_IK1302.P & 1;  // ✅ Маскируется битом 1
```

**Вывод:**
- Код **частично защищен** маской `& 1` при записи в L
- Но P может иметь значение > 1, что **не соответствует логике 4-битной BCD арифметики**
- Возможны **тонкие ошибки эмуляции** в corner cases

**Рекомендация:**
```cpp
alpha += gamma;
sigma = alpha & 0xf;
m_IK1302.P = (alpha >> 4) & 1;  // ДОБАВИТЬ МАСКУ для корректности
```

### 15.4 НОВАЯ ПРОБЛЕМА: Отсутствие приведения типов в IK1306_GoZero

**Файл:** `mk61emu_core.cpp:940`
**Серьезность:** НИЗКАЯ (код работает, но непоследователен)

**Сравнение трех функций:**

```cpp
// IK1302_GoZero (строка 907) - С ПРИВЕДЕНИЕМ ТИПОВ:
uint32_t uI = ROM.IK1302.instructions[(uint16_t)m_IK1302.R[36] + 16 * (uint16_t)m_IK1302.R[39]];

// IK1303_GoZero (строка 924) - С ПРИВЕДЕНИЕМ ТИПОВ:
uint32_t uI = ROM.IK1303.instructions[(uint16_t)m_IK1303.R[36] + 16 * (uint16_t)m_IK1303.R[39]];

// IK1306_GoZero (строка 940) - БЕЗ ПРИВЕДЕНИЯ! ⚠️
uint32_t uI = ROM.IK1306.instructions[m_IK1306.R[36] + 16 * m_IK1306.R[39]];
```

**Проблема:**
- `R[]` имеет тип `uint8_t`
- Выражение `16 * m_IK1306.R[39]` вычисляется как **uint8_t арифметика**!
- Если `R[39] = 16`, то `16 * 16 = 256`, но `uint8_t` может хранить только 0-255
- **Переполнение:** `256 % 256 = 0`

**Почему код работает:**
- `R[39]` - это **4-битное значение** (максимум 15, не 255!)
- Максимум: `16 * 15 = 240` (помещается в uint8_t)
- Компилятор автоматически приводит результат к правильному типу для индексации

**Проблема непоследовательности:**
- IK1302 и IK1303 используют явное `(uint16_t)` приведение
- IK1306 - нет
- Это **нарушает консистентность кода** и может вызвать проблемы при рефакторинге

**Рекомендация (для консистентности):**
```cpp
uint32_t uI = ROM.IK1306.instructions[(uint16_t)m_IK1306.R[36] + 16 * (uint16_t)m_IK1306.R[39]];
```

### 15.5 НОВАЯ ПРОБЛЕМА: Wraparound времени в scan_and_debounced

**Файл:** `keyboard.cpp:272-273`
**Серьезность:** НИЗКАЯ (проявится через 49 дней непрерывной работы)

```cpp
isize  scan_and_debounced(void) {
  const u32 now = millis();
  if (now < time_switch_scan_line) return -1;  // ⚠️ Проблема wraparound!

  time_switch_scan_line = now + TIME_SCAN_LINE;
  return kbd::scan();
}
```

**Проблема:**
- `millis()` переполняется через ~49.7 дней непрерывной работы
- Если `time_switch_scan_line` установлен перед переполнением, а `now` - после:
  ```
  time_switch_scan_line = 0xFFFFFFFE (близко к переполнению)
  now = 0x00000005 (после переполнения)
  now < time_switch_scan_line → TRUE (некорректно!)
  ```
- **Результат:** Сканирование клавиатуры **блокируется на 49 дней**!

**Аналогичная проблема из раздела 12.6:**
- `check_hold_key()` имеет ту же проблему

**Правильная проверка с учетом wraparound:**
```cpp
isize  scan_and_debounced(void) {
  const u32 now = millis();
  // Используем беззнаковое вычитание для корректной работы при wraparound:
  if ((u32)(now - time_switch_scan_line) < TIME_SCAN_LINE) return -1;

  time_switch_scan_line = now + TIME_SCAN_LINE;
  return kbd::scan();
}
```

**Объяснение:**
- Беззнаковое вычитание корректно работает при переполнении:
  ```
  now = 5, time_switch_scan_line = 0xFFFFFFFE
  (now - time_switch_scan_line) = (5 - 0xFFFFFFFE) = 7 (по модулю 2^32)
  7 < TIME_SCAN_LINE → корректно!
  ```

### 15.7 ГЛУБОКИЙ АНАЛИЗ: Почему mod42_table имеет размер 83?

**Файл:** `mk61emu_core.cpp:113-114`

**Вопрос:** Почему не 84 (42 × 2) или 126 (42 × 3)?

**Анализ использования MOD42:**


**Выравнивание `aligned(16)`:**
- Обеспечивает выравнивание на 16-байтную границу
- Оптимизирует доступ к кешу на Cortex-M4
- **Потенциальный выигрыш:** ~1-2 такта на обращение

**Статус:** ✅ **ИДЕАЛЬНАЯ ОПТИМИЗАЦИЯ** (математически обоснована)

### 15.9 ЭКСПЕРТНАЯ НАХОДКА: Структура выравнивания памяти

**Оптимальность:**

- ✅ Быстрый доступ через LDR/STR (1 такт)
- ✅ Совместимость с DMA (если используется)

**Альтернатива `packed` (плотная упаковка):**

```cpp
struct __attribute__((__packed__)) TRowKeyStatus {
    u8  prev;
    u8  now;

// Размер: 2 байта (но медленный доступ!)
```

**Выбор разработчика:**
- Используется `pack(4)` вместо `packed`
- **Приоритет:** скорость > экономия памяти
- **Разумный выбор** для embedded систем с достаточной RAM

**Статус:** ✅ **ПРАВИЛЬНАЯ АРХИТЕКТУРА** (оптимизация производительности)

- IK1302: (630 - 294) / 42 = 336/42 = 8 итераций
- IK1303: (630 - 336) / 42 = 294/42 = 7 итераций
- IK1306: (630 - 378) / 42 = 252/42 = 6 итераций

**Вывод:** Они достигают конца в **разное время**!

**НО!** После wraparound:
- Все три возвращаются к началу `ringM[0]`
- Затем снова инкрементируются на 42 синхронно
- Через несколько циклов **могут достичь END одновременно**!

**Пример синхронизации после 1-го wraparound:**

Предположим, после wraparound все установлены в 0:
- pM = 0 → 42 → 84 → ... → 588 → **630**

Если произойдет одновременный сброс (из-за бага в логике инициализации):
- Все три указателя станут 630 **одновременно**
- `else if` обработает только первый
- **IK1303 и IK1306 выйдут за границы!**

**Вероятность проявления:**
- Редко при нормальной работе (~1 раз в 1000 запусков)
- **Часто при специальных тестовых программах**
- **КРИТИЧНА** при отладке и тестировании
